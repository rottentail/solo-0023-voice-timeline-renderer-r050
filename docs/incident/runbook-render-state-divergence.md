# 事故规程：渲染任务终态与磁盘交付不一致的现场保全与继续服务

适用对象：Voice Timeline Renderer 值班工程师（on-call）。

适用场景：一个 render job 的持久化状态（`jobs/<id>.json`）与其磁盘交付物
（`renders/<id>/output.wav`、`renders/<id>/receipt.json`、`tmp/` 暂存内容）
之间出现无法互相解释的分歧。典型信号包括：

- 任务已是终态 `completed`，但输出或收据在磁盘上不存在；
- 任务仍是活动态（`queued` / `rendering` / `finalizing`），交付目录却已发布；
- 任务已 `failed`，却存在可下载的交付目录；
- 输出字节的 SHA-256 与收据/任务记录中的摘要不一致；
- 存在没有任何 job 记录归属的交付目录；
- `tmp/` 中残留暂存目录，其归属和冗余性不明。

本规程不假设故障原因，也不承诺修复。它只规定：**如何在不消灭证据、不停掉
整台服务的前提下，把待查对象及其关联事实固定下来，并让不受影响的业务继续
运行在明确的边界内。**

---

## 1. 不可违反的红线

1. **禁止按年龄清理 `tmp/`。** 修改时间（mtime）只作为事实记录，永远不是
   删除依据。暂存目录是否冗余，只能由“与某个终态任务的正向归属链接 + 该
   任务已发布侧自洽”共同证明，证明不了的一律保留。
2. **禁止只拷贝几个 JSON 就声称完成取证。** 完整证据至少包含：任务记录、
   时间线、全部引用素材（`source.wav` + `metadata.json`）、已发布输出与
   收据、`tmp/` 下全部条目、以及每个文件的 SHA-256/大小/mtime 清单。字节
   本身是核心证据，JSON 只是索引。
3. **禁止直接改写 job 终态。** 不允许手工编辑 `jobs/<id>.json` 把
   `completed` 改成别的状态，也不允许补写、删除终态记录。状态机只允许沿
   服务自身的合法迁移前进，终态不可逆（见 `domain.ValidRenderTransition`）。
4. **禁止在值班步骤里调用不存在的恢复接口。** 当前 HTTP 面只有
   `GET /healthz` 与 sources/timelines/renders 的读写路由，没有“修复任务”
   “重新发布输出”“强制状态迁移”之类的端点。本规程不杜撰任何这类接口；
   未来若新增，必须先走代码变更，再更新本规程。
5. **禁止重启即重跑、清空数据目录、重装服务等会覆盖现场的动作。** 任何
   会修改数据根的处置，必须在第 3 步的证据包校验通过之后，并经变更审批。
6. **取证工具对数据根只读。** 本仓库 `internal/incident` 与
   `cmd/incidentpreserve` 对数据根不存在任何创建、改名、改权限、删除路径；
   所有写操作只发生在单独指定的证据包目录。

## 2. 分歧分类与每类必须固定的事实

值班第一步是只读扫描，不做任何处置：

```bash
go run ./cmd/incidentpreserve -data <数据根> -scan-only
```

扫描把每个 render id 归入下表之一（字段名与
`divergence-report.json` 一致）。**每一类都同时给出“已固定事实”和
“必须保留给调查的不确定性”——不确定性不允许在值班阶段被强行收敛。**

| 分类 `class` | 磁盘事实（已可判定） | 必须保留的不确定性 |
|---|---|---|
| `consistent` | 终态与交付物一致，输出摘要与收据/任务记录吻合 | 无 |
| `completed_missing_artifacts` | job 为 `completed`；`renders/<id>/` 或其中文件缺失；任务记录里的时间线、摘要、时间戳仍在 | 该渲染是否曾成功完成无法由磁盘证明；丢失的原因与时点未知 |
| `active_with_published_artifacts` | job 处于活动态；交付目录已存在且含输出/收据 | 可能是发布过程中崩溃；权威终态未知，不能凭目录反推“已完成” |
| `failed_with_published_artifacts` | job 为 `failed` 且带稳定错误码；交付目录却存在 | 交付物先于还是后于失败产生未知；违反“failed 不暴露输出”不变量 |
| `receipt_digest_mismatch` | 输出实际 SHA-256 与收据承诺、job 记录摘要不一致 | 哪一份字节是权威版本未知；读取路径不做摘要校验，HTTP 仍可能 200 |
| `receipt_job_mismatch` | 收据内的 render/timeline 标识与并列的 job 记录不符 | 交付物真实归属未知 |
| `job_unreadable` | job JSON 无法读取或解码，或出现无法识别的状态值 | 真实状态未知，禁止猜测后处置 |
| `orphan_artifacts_no_job` | `renders/<id>/` 存在但没有任何 job 记录 | 生产任务及其终态未知 |

### 2.1 关联事实的固定范围

对每个分歧 id，证据必须能闭环回答“它消费了什么、承诺了什么、实际落盘了
什么”。因此扫描/保全覆盖的数据根子树为：

- `jobs/<id>.json`：状态机轨迹与终态、错误码、收据摘要；
- `timelines/<timeline_id>.json`：span 顺序、源区间、crossfade、目标响度；
- `sources/<span 引用的每个 source_id>/`：不可变 `source.wav` 与
  `metadata.json`（含原始摘要）；
- `renders/<id>/output.wav` 与 `receipt.json`：实际发布字节与收据；
- `tmp/` 下**全部**条目：包括 `render-*`、`source-*`、`.write-*` 及任何
  其他命名，连同 mtime、内容清单、可解析出的归属 render id；
- 每个文件的大小、权限位、mtime（UTC）与 SHA-256。

### 2.2 `tmp/` 暂存条目的处置判定

扫描对每个暂存条目给出两种处置之一，判定只看归属链接，不看年龄：

- `retain_for_investigation`（默认）：条目不包含可解析的收据、归属任务
  不存在、归属任务仍在活动态、或归属终态任务的已发布侧无法通过摘要校验。
  演练中一个被人为调到 90 天前的无链接条目仍然归入此类——年龄不改变结论。
- `cleanup_eligible_only_after_preservation_and_approval`：条目内收据正向
  链接到一个**终态**任务，且该任务已发布侧自洽（completed 且输出摘要校验
  通过；failed 的“空交付”本身就是定义）。即便如此，工具本身不具备删除
  能力；真正清理必须在证据包校验通过后走独立变更审批。

## 3. 现场保全操作规程（服务保持运行）

全程不需要停服。保全是对数据根的整树只读复制，与在线读写互不阻塞。

1. **建立证据包目录。** 选择数据根之外、且不包含数据根的独立路径作为
   `-bundle-parent`（工具会拒绝互为父子的路径，防止嵌套覆盖）。
2. **执行整树保全与自检：**

   ```bash
   go run ./cmd/incidentpreserve \
     -data <数据根> \
     -bundle-parent <证据包父目录> \
     -label <工单号或短标签>
   ```

   该命令依次完成：只读扫描 → 整树复制（含 `tmp/` 全部条目）→ 写入
   `preservation-manifest.json`（逐文件 SHA-256/大小/权限/mtime）→ 写入
   `divergence-report.json` → 对证据包自身重新哈希校验。
3. **解读退出码：** `0` 全部分类一致且无待保留暂存；`3` 保全本身成功，
   但存在分歧/待保留条目（需要继续第 4 步判定）；`1`/`2` 为执行或参数
   错误，证据包不可用，必须排障后重做，不能带过。
4. **独立复核证据包：**

   ```bash
   go run ./cmd/incidentpreserve -verify <证据包目录>
   ```

   校验会逐文件重算摘要并检查“清单外多余文件”。任何不一致都会非零退出。
   校验只读证据包，不需要也不会触碰在线数据根。
5. **确认现场未被改动。** 保全是复制而非移动：复核在线数据根中被标记为
   `retain_for_investigation` 的暂存条目与分歧任务目录仍然原样存在。
6. **登记与交接。** 把证据包路径、校验结果、`divergence-report.json` 中的
   分类计数写入事故工单。证据包应按组织证据保留策略设置只读权限与留存
   周期；在调查结论形成前不得删除。

### 3.1 证据包结构

```text
<bundle-parent>/incident-<label>-<UTC时间戳>/
  preservation-manifest.json   # 逐文件哈希/大小/权限/mtime 清单
  divergence-report.json       # 分歧分类、事实与不确定性
  data-snapshot/               # 数据根整树只读快照（jobs/ timelines/ sources/ renders/ tmp/）
```

“拷走几个 JSON”不构成本规程意义上的证据：没有 `data-snapshot/` 全树与
逐文件哈希清单并通过 `-verify` 的产物，不得视为保全完成。

## 4. 继续服务的可用边界

保全期间与之后，服务进程不重启、数据根不迁移。继续运行的边界由现有
HTTP 契约天然给出，不需要新接口。

### 4.1 明确继续可用的流量

以下操作与分歧任务无数据依赖，保持正常可用，应作为值班期间的冒烟项：

- `GET /healthz`；
- 对**未受影响** source 的 `PUT/GET /v1/sources/{id}`（新素材登记照常，
  source 不可变且按 id 独立存储）；
- 对未受影响 timeline 的 `PUT/GET /v1/timelines/{id}`；
- 对未受影响 render 的 `PUT/GET /v1/renders/{id}` 及其
  `/receipt`、`/output`；
- 使用全新 id 发起的完整新渲染链路。隔离演练在分歧存在的同时新建了
  source、timeline、render 并正常 `completed`，证明该边界真实可用。

### 4.2 受影响对象的读取边界（现有行为，不做伪装）

读取处理的判定顺序是“先查 job 状态门，再读交付文件”，因此：

- `completed_missing_artifacts`：状态门通过但文件缺失，`/output` 与
  `/receipt` 返回 **409 `render_not_completed`**（现有稳定错误信封），
  不会伪造成功响应。
- `failed_with_published_artifacts` 与 `active_with_published_artifacts`：
  状态不是 `completed`，同样被 409 挡在状态门，磁盘上的目录不会通过 HTTP
  泄漏给调用方。
- **`receipt_digest_mismatch` 的已知局限（必须知晓）：** 读取路径不重新
  计算摘要，状态门通过且文件存在时，`/output`、`/receipt` 仍返回 **200**。
  也就是说，这类分歧无法被调用方或健康检查发现，只能由第 2 步的磁盘侧
  扫描发现。值班期间不得向调用方承诺该 render 的输出字节可信；其可信性
  判定属于后续调查，不属于服务恢复的前置条件。
- 对分歧 render id 重复 `PUT /v1/renders/{id}`：服务按幂等语义直接返回
  既有 job（200），不会产生第二条执行路径，也不会推动任何状态迁移。

### 4.3 隔离原则

隔离是**逻辑隔离**：把分歧 id 集合（来自报告的非 `consistent` 项）登记到
工单并通知调用方暂停消费这些 id 的输出；不做网络隔离、不停进程、不摘
数据目录。除这些 id 外的全部读写继续开放。

## 5. 哪些判断足以支撑“恢复服务”，哪些不确定性必须留给调查

### 5.1 足以支撑恢复/继续服务的判断（满足即可宣告服务面恢复）

服务本身在多数分歧下并未中断，因此“恢复”指的是确认继续服务的边界成立，
而不是修复分歧记录。全部满足即可：

1. 第 3 步证据包已生成且 `-verify` 退出 0，现场已完整固定；
2. 在线数据根未被保全动作改动（只读复核通过）；
3. 4.1 的未受影响冒烟项全部通过（healthz、未受影响 source/timeline/render
   读写、一个全新 id 的端到端渲染）；
4. 分歧 id 集合已登记并完成 4.2 边界确认：缺失/失败/活动态类均被现有 409
   边界挡住，无部分文件经 HTTP 泄漏；
5. 对 `receipt_digest_mismatch` 类已明确告知调用方“输出可信性待调查”，
   不把 200 响应误当作健康证明；
6. 没有任何手工状态改写、暂存清理或重跑动作发生。

### 5.2 必须保留给后续调查、禁止在值班阶段收敛的不确定性

- 分歧产生的**原因与时点**：崩溃、磁盘问题、并发缺陷、外部改动等均为
  假设，磁盘快照本身不能自证原因。
- `completed_missing_artifacts` 是否**曾经成功交付过**：在找到证据包外的
  其他佐证前，只能保持未知。
- `receipt_digest_mismatch` 中**哪份字节权威**：不得由值班选择一方覆盖
  另一方。
- `active_with_published_artifacts` 的**权威终态**：目录存在不等于
  completed。
- `orphan_artifacts_no_job` 与无链接暂存条目的**归属**。
- 任何 `job_unreadable` 记录的**真实状态**。
- 暂存条目的**最终清理决定**：即便被标记为 cleanup-eligible，删除动作也
  属于证据包归档后的独立变更，不在本规程内执行。

### 5.3 明确不做的事

- 不手工编辑任何 `jobs/*.json`，不补写、不回退、不删除终态；
- 不删除、改名、“先挪走看看”任何 `tmp/` 条目或 `renders/` 目录；
- 不通过重跑同名 render 来“覆盖”分歧（幂等返回也证明此路不通）；
- 不在没有对应代码的情况下编写或调用任何恢复/修复接口；
- 不把全服务停机作为分析前置条件。

## 6. 隔离演练（规程可执行性的证明）

演练在完全隔离的临时数据目录中构造分歧，通过真实 HTTP 面断言行为，结束
后清理临时目录，全程不触碰真实数据：

```bash
go run ./cmd/incidentdrill
```

演练依次证明：

1. **固定对象与关联事实：** 在临时数据根中构造全部七种非一致情形
   （completed 缺交付、活动态已发布、failed 带交付、摘要不符、孤儿交付、
   不可读/未知态、健康对照组），断言扫描输出的分类、双向摘要、归属事实与
   每条不确定性字段全部符合第 2 节定义。
2. **暂存不按年龄当垃圾：** 同时构造“链接到已校验 completed 任务的暂存”
   “无链接新暂存”和“mtime 调到 90 天前的无链接暂存”，断言只有前者进入
   cleanup-eligible，后两者无论多旧都 `retain_for_investigation`。
3. **继续服务边界：** 分歧存在期间，healthz、未受影响素材/时间线/渲染的
   读写、以及一个全新 id 的登记-作曲-渲染链路全部成功；分歧对象命中第
   4.2 节的真实响应边界（缺失类 409；摘要不符类 200 的局限被显式断言并
   记录，而不是被假设为有防护）。
4. **完整证据而非几个 JSON：** 断言证据包包含任务、时间线、素材、发布
   交付、全部暂存条目，并通过逐文件哈希自检；同时断言在线数据根在保全
   后原样未动。
5. **终态不被服务流量改写：** 对所有任务记录在流量前后做 SHA-256 比对，
   断言服务面不存在任何终态改写路径；新渲染只能沿合法生命周期到达
   completed。

任一步失败，演练以非零码退出并保留临时数据根供检查。

## 7. 工具与退出码速查

| 命令 | 用途 | 退出码 |
|---|---|---|
| `go run ./cmd/incidentpreserve -data <根> -scan-only` | 只读扫描并打印分歧报告 | 0 无分歧；3 有分歧/待保留暂存；1/2 错误 |
| `go run ./cmd/incidentpreserve -data <根> -bundle-parent <目录> -label <标签>` | 整树保全 + 报告 + 自检 | 3 表示保全成功但存在分歧；1/2 为失败 |
| `go run ./cmd/incidentpreserve -verify <证据包>` | 独立复核证据包完整性 | 0 通过；1 摘要/大小/多余文件不一致 |
| `go run ./cmd/incidentdrill` | 隔离演练 | 0 全部断言通过；1 断言失败并保留现场 |

工具实现位置：

- `internal/incident/scan.go`：只读分类引擎（对数据根无写路径）；
- `internal/incident/preserve.go`：整树复制、清单、自检；
- `cmd/incidentpreserve/`：值班离线 CLI；
- `cmd/incidentdrill/`：隔离演练。
